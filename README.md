# hcjackchen-tbench-multiturn

Multi-turn terminal-bench tasks (T-Bench 2.0 multi-step track) — each task is a chain of 2-3 steps where the agent must carry context (following) or pivot (overriding).

This repo is separate from `hcjackchen-tbench-1` (single-turn) to keep multi-turn metadata clean.

## Structure

Each task lives in its own directory:

```
<task-slug>/
├── task.toml              # schema_version = "1.1", [[steps]] chain, tags BEFORE steps
├── dossier.md             # privileged author notes (litmus per step + S1/S2/S3 + mechanism + recall_resistance + partial_failure + predicted cascade + env spec + oracle chain)
├── environment.spec.md    # Dockerfile recipe FROM ECR, pinned deps, fixtures for all steps
├── steps/
│   ├── 1_<name>/instruction.md   # FINAL English symptom-only, Codex MUST NOT edit
│   ├── 2_<name>/instruction.md   # terse follow-up relying on carried context
│   └── 3_<name>/instruction.md   # if 3 steps — legible motivated pivot with absence assertion
└── .meta/handoff.json     # machine manifest (canary GUID, stepArtifacts, overExecMap, mechanism)

# After Codex Phase2 build (gradeable bundle):
<task-slug>/
├── environment/Dockerfile       # FROM public.ecr.aws/docker/library/... pip install pytest
├── steps/
│   ├── 1_<name>/
│   │   ├── instruction.md       # symptom-only (READ-ONLY)
│   │   ├── solution/solve.sh    # oracle that scores 1.0, chmod +x, canary GUID
│   │   └── tests/{test.sh,test_outputs.py}
│   ├── 2_<name>/...
│   └── 3_<name>/...
└── task.toml
```

## Authoring flow — Phase 1 (MetaCode) → Phase 2 (Codex)

**Phase 1 — Ideation (this repo, human + MetaCode):**
- Write per-step `instruction.md` (symptom/end-goal only, never cause/file/fix, preserve literal tokens verbatim: paths, filenames, flags, env vars, code, column headers, error wording, output contracts).
- Write `dossier.md` with:
  - one-line litmus per step defended
  - per-step diagnosis + cross-step S1/S2/S3 why not decorative
  - mechanism chain load-bearing
  - recall_resistance per step + partial_failure per step+cross-step (concrete >=1/5)
  - predicted cascade rates (weak mostly fails, Avocado/Opus >=1/5 pass & >=1/5 fail among reaching)
  - hidden-test plan held-out disjoint + over-exec negatives from later identifiers ONLY + regression
  - env spec ECR pinned + canary GUID fresh uuid4
  - oracle-chain sketch self-contained
- Write `environment.spec.md` (Dockerfile FROM ECR, `pip install pytest`, pinned deps covering ALL steps, deterministic mtimes, git history if needed).
- Write `task.toml` skeleton schema 1.1: tags BEFORE [[steps]], inherit_prior_session=true on 2+, min_reward=1.0, timeout 1800, no root [verifier]/[agent].
- Write `.meta/handoff.json`.

**No `solution/`, `tests/`, `environment/Dockerfile`, `README` yet — Codex builds.**

**Phase 2 — Build (Codex):**
- Consumes `<outDir>/<slug>/` — treats `steps/*/instruction.md` READ-ONLY.
- Derives hidden tests from identifiers in steps + dossier plan (held-out disjoint, positives+negatives+regression, over-exec negatives from later identifiers ONLY).
- Must satisfy: DO-NOTHING FAIL per step (tests FAIL before solve), ORACLE 1.0 chain end-to-end, GREEN >0 executed 0 skipped per step, OVER-EXEC negatives trip.

Validation:

```bash
python3 <skill-dir>/scripts/check_catalog_uniqueness.py <outDir> --verbose   # X1 clones + X2 fiction + mechanism + tags + hard gates
python3 <skill-dir>/scripts/build_catalog.py <workflow-output>              # INDEX.md + REJECTED.md
python3 <skill-dir>/scripts/run_oracle_chain.py <outDir>/<slug>             # docker chain proof
```

## Multi-turn bar

Per `tbench-task-authoring-multiturn-ideation` skill:

- **2 dynamics:** context-following (relies on unrepeated carry: area/file/conventions) or context-overriding (pivots away motivated, old approach must be removed + absence tested). Favor overriding + 3 steps (pool skewed following+2).
- **3-signal non-decorative per N-1→N:** S1 oracle coupling uses step N-1 output, S2 instruction non-duplication (no re-pinning), S3 test adaptation to specific prior output. If >=2 no, decorative — ship single-turn.
- **Over-execution guarded:** per boundary negatives drawn ONLY from identifiers later steps explicitly name (function, config key, file path, class, table column). Pre-revealed future destroys signal.
- **Per-step complexity floor + difficulty signature + 5-gate kill + sharp screens:** same bar as single-turn but PER STEP + cross-step coupling (losing context/pivot/over-exec/regression).
- **Cross-round feasibility:** single shared env covers every step, oracle CHAIN 1.0 end-to-end no starved resource.

## Seed ideas

Promoted from `hcjackchen-tbench-1/Ideas/` (74 single-turn dossiers) that have not yet been submitted:

- `tbench-database-internals-tasks` (25) — byte-exact LOB recovery across 3 artifacts, LSM compactor anti-canonical, etc.
- `tbench-filesystem-internals-tasks` (15) — ext4 carved inode, VFAT anti-canonical, etc.
- `tbench-recsys-tasks` (15) — HNSW interrupted compaction, PQ codec, etc.
- `tbench-robotics-3d-recon-tasks` (9) — BA converges but structure fails white-box, etc.
- `tbench-trading-catalog` (10) — l3-l2 rebuild, cumulative vs incremental fill, etc.

Each single-turn's internal chain (detect→localize→rebuild→resolve) already rich for split-then-pivot:

- split internal chain (following): step1 stop losing data complete, step2 ensure ordering relying on unrepeated area/file
- extend then pivot (overriding preferred): step1 core (original), step2 extends (add metrics without restating token bucket/Redis/key), step3 profile says sorted too slow → switch to hash map drop ordering + absence assertion

See `Ideas/single-to-multiturn-promotion.md` for promotion patterns.
