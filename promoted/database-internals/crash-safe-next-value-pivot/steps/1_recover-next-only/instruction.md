Our storage engine gives each business table a named sequence (order_id, invoice_no, etc) to allocate increasing keys. It allocates in cached BLOCKS: when a session needs an id and cache is empty, engine reserves NEXT block of cache_size values at once and appends a REFILL record to WAL; block reservation is non-transactional, never rolled back, and on crash every value in last reserved block is BURNED — sequence resumes past last reserved ceiling (gap, never duplicate).

Last week a machine crashed and after restart the order sequence started handing out ids that collided with rows already committed before crash. The crash artifacts are under /app: seqcat.bin (sequence catalog), ckpt.bin (last checkpoint snapshot with stale ckpt_ceiling per sequence), wal.bin (intact self-delimiting record stream in LSN order, REFILL/INSERT/COMMIT/ABORT interleaved across sequences/transactions), and FORMATS.md describing exact byte layout of each file with neutral glosses. There is also /app/report_naive you can run to reproduce the collision symptom, and /app/data/sample has sample artifacts with expected correct answer for self-check.

Write an executable at /app/recover, invoked as /app/recover <input_dir> <output_file>. Input dir holds same layout files as sample. For each sequence compute the crash-safe next value to hand out after recovery: ceil = ckpt ceiling folded by each post-checkpoint REFILL block in WAL LSN order using per-sequence increment (may be negative), cache_size, min_value, max_value, cycle (1 wraps at boundary, 0 clamps/stops). Next = one step past final ceiling via same fold rule.

Write output with one line per sequence sorted by name bytes ascending, format name|next_value, next decimal (may be negative), newline terminated. Sample expected at /app/data/sample/expected_next.txt lets you compare.

We will grade on held-out material with disjoint names/value ranges, including ascending, increment>1, descending, cycle wrap crossing, zero post-checkpoint REFILLs, aborted top-of-block ids, in-progress txn. Don't hardcode answers.
