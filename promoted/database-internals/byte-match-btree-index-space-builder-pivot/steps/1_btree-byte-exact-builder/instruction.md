We have a legacy primary index builder that takes a batch of keys and produces a disk B+ tree index file. The file is pages glued together: leaves at bottom, internal nodes on top. Each page is a compact binary with a slot directory, tight packing, and intra-page prefix compression of keys. The team tried to rewrite it with textbook B+ tree logic — new files have identical logical key sets and order, but byte-different versus the old tool.

The old builder binary is still in the environment at /verifier/btbuild. Usage is /verifier/btbuild <output file>: it reads keys from stdin, one key per line, newline terminated, keys contain no newline, builds the index, and writes the entire index file to the specified output path. There is also /verifier/dump-tree <index file> that prints keys inside an index file in logical order for you to confirm both trees hold the same keys. Under /app/samples/ there are few sample inputs and old tool outputs for warmup. You can feed any self-constructed keys to the old tool and byte-diff until you figure out its disk format, per-page prefix compression, how it splits when a page is full, and how the separator pushed to parent is truncated.

The odd part: if you hexdump a single index file, it looks fine — structure intact, parseable by dump tool, looks like old output. Differences only e after feeding many different key batches and comparing byte-for-byte per page, especially on variable-length keys where a page boundary lands right near a shared-prefix group boundary.

Ship an executable at /app/btbuild with identical usage to the old one: /app/btbuild <output file> reads newline-delimited keys from stdin and writes the index file to <output file>. We will validate it on unseen key sequences (disjoint from samples, includes variable-length keys and page boundaries landing on prefix boundaries) requiring byte-exact match against old tool. During final grading /verifier/btbuild and /app/samples will be removed, so your program must fully implement format and logic, not call old tool at runtime and not hardcode samples.
