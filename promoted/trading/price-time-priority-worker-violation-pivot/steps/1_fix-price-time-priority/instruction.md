We have a multi-threaded quote/order gateway at /app/gateway.py. It replays a tick event stream in JSONL format where each line is one event: {"oid":int,"sym":str,"side":"BID"|"ASK","price":int,"qty":int,"action":"ADD"|"TAKE"}. ADD rests an order at (sym,side,price), TAKE is an incoming marketable order that sweeps the resting queue at that (sym,side,price) for qty. The gateway is invoked as python3 /app/gateway.py <feed_file> <output_file> and writes all fills as a JSON array of {"taker":oid,"maker":oid,"price":int,"qty":int} in execution order.

Recently replaying high-frequency feeds shows a subtle bug: at the same price level where many makers rest, the fill order is wrong — a later arriving maker fills before an earlier arriving one, sometimes stealing quantity that should have gone to the earlier order. With tiny feeds or when forcing the thread pool to one worker, results look perfect. Under realistic-rate large replay with heavy same-price clustering, inversions appear intermittently. The program never errors and never drops events.

Check /app/sample/feed.jsonl and its correct result /app/sample/expected_fills.json for format and semantics. Fix the gateway so that for any same-format feed, at each price level makers fill strictly in arrival order (arrival = feed line order), and repeated runs on the same feed are stable and byte-identical. Keep output format unchanged: JSON array of {"taker","maker","price","qty"} in execution order. We will test with additional feeds using disjoint order ids and prices from the sample, so do not hardcode the sample.
