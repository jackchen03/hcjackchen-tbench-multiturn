We have a small tool at `/app/rebuild.py` that rebuilds an aggregated L2 book from an L3 order-by-order feed. Usage is `python3 /app/rebuild.py <feed_file> <output_json>`. It reads the feed line by line, maintains resting order state, and writes the final aggregated book to the output path you give it.

A sample is in `/app/sample/` with `feed.txt` and the correct book `expected.json` for that feed. If you run `python3 /app/rebuild.py /app/sample/feed.txt /tmp/out.json` and compare to `/app/sample/expected.json`, the rebuilt book diverges — some price levels show double the volume or missing orders, sometimes size goes negative, best bid can cross best ask, and the top-of-book is wrong. The feed itself looks well-formed — every line has valid fields like `order_id`, `price`, `quantity`, `side` — you only see the problem after replaying to L2 and reconciling per level.

The feed contains event types `ADD`, `CANCEL`, `EXEC`, `TAPE` (mapped in the file as `A|seq|order_id|side|price|size`, `X|seq|order_id|size`, `E|seq|order_id|exec_size`, `T|seq|exec_id|order_id|price|exec_size`). There is also `REPLACE` as `R|seq|old_order_id|new_order_id|new_price|new_size` and `REPRICE` as `P|seq|order_id|new_price|new_size` (same order_id, price move preserving priority) which will be handled later. For this first step, focus only on correctly handling `ADD`, `CANCEL`, and distinguishing `E` (book-affecting execution that reduces resting size) vs `T` (tape-only print that does NOT affect L2 book) — naive rebuild applies both execution streams to the book and keeps stale price levels, double counting. Leave `REPLACE` and `REPRICE` handling broken for now; they will still show double counts in this step's sample but should not be fixed yet — the next steps will address atomic REPLACE and in-place REPRICE.
