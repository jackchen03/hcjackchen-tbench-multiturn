Our post-close multilateral settlement obligations run is broken.

Program at /app/settle.py is invoked as `python3 /app/settle.py <messages_file> <output_file>`. It reads a full day of deal messages as JSONL, one line per message with fields `msg_type` in {NEW, AMEND, CANCEL}, `trade_id` (string), `counterparty` (string), `trade_date` (YYYY-MM-DD string) and for NEW/AMEND the full FX state: `bought_ccy`, `bought_amount` (int micros), `sold_ccy`, `sold_amount` (int micros). AMEND carries the complete corrected state — it may change trade_date, either currency, and amounts. CANCEL carries only trade_id. Multiple messages per trade_id appear in file order.

Each FX trade contributes two legs under a single value_date into buckets keyed by (counterparty, currency, value_date): +bought_amount in bought_ccy and -sold_amount in sold_ccy. Value_date is NOT in the message; it is computed as spot(trade_date, bought_ccy, sold_ccy) = T+2 business days rolled over holiday calendars stored in /app/calendars/ as <CCY>.txt (one ISO date per line, e.g. /app/calendars/USD.txt). A sample is shipped at /app/sample/messages.jsonl with custodian ground truth at /app/sample/expected.csv you can use to check.

Symptom: summing net_amount across all buckets matches custodian totals, but per (counterparty, currency, value_date) bucket splits are wrong. The wrong buckets are concentrated on names that had AMEND messages that day, especially when the corrected date lands around month-end or quarter-end holidays. Individual message fields look normal. Only running the report and diffing per bucket against the custodian truth reveals the mismatch.

Fix /app/settle.py so for any same-format message stream it produces exactly the custodian-correct settlement list, not just passing the sample. Keep the existing CLI and output format unchanged: output is CSV, first row header `counterparty,currency,value_date,net_amount`, then one row per non-zero bucket; value_date as YYYY-MM-DD, net_amount as integer micros (receive positive, pay negative); only rows with net_amount != 0; sorted by counterparty, currency, value_date ascending.
