We have an internal tool that takes an ordered list of long filenames and writes the raw FAT directory region as raw bytes — a stream of 32-byte entries (LFN slots with attribute 0x0F plus the corresponding 8.3 short entry in emission order). The original binary lives at /app/reference/vfatdir and is used as vfatdir <names.txt> <out.bin> : the first argument is a text file with one UTF-8 long name per line in insertion order, the second is the output file path to write the raw bytes. Source is lost; only a stripped native executable remains, and it will be deleted during grading — you cannot call it at grade time.

Shipped samples are at /app/samples/ with names-*.txt and corresponding oracle dir-*.bin for comparison. System has mtools (mdir, mcopy, minfo), dosfstools, sqlite3 to study canonical FAT layout in unmounted mode, but the oracle does NOT match those standard tools. Its short-name mangling, LFN slot count, and NTRes byte handling diverge.

Implement /app/myvfatdir as an executable with identical CLI: myvfatdir <names.txt> <out.bin> writing the directory bytes to the second path. Grading will run /app/myvfatdir on held-out name lists you have never seen and compare byte-identical (exact length and every byte) versus the oracle's output for same list. Must match exactly to pass. Do not hardcode samples.
