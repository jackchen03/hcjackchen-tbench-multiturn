Our storage appliance has a log-recovery tool that reads a base image and a journal file and replays the committed changes onto the base to produce a recovered image. The verification pipeline trusts that recovered image byte-for-byte, but we lost the source and only have a runnable binary left. You need to differentially reimplement that nonstandard journal replayer as a drop-in replacement that produces byte-identical output for any base and journal.

The oracle binary is at /app/reference/jrecover and its CLI is jrecover <base image> <journal file> <output image> — for example jrecover base.img changes.jnl out.img writes the recovered image to the path you specify. It runs fine right now and you can probe it freely on images and journals you craft yourself to figure out which changes commit, which are discarded, and what each block ends up as. At grading time this reference binary will be deleted, so you may not call it at runtime — you must fully reimplement the logic.

Put your implementation at /app/myrecover as an executable whose CLI is identical: myrecover <base image> <journal file> <output image>. The harness will run /app/myrecover on held-out (base image, journal file) pairs and compare its output image byte-for-byte to what the original /app/reference/jrecover would have produced for the same inputs. Only an exact match counts.

Under /app/samples/ there are a few sample triples: base images base-*.img, journals journal-*.jnl, and the recovered images recovered-*.img that the original tool produced for them. The system has e2fsprogs installed (mke2fs, debugfs, dumpe2fs etc.) that you can use without mounting to craft and inspect images, but you must reverse-engineer the journal file format itself from the oracle's behavior. The graded journals will cover trickier cases than the samples, including revoke edge cases, escaped data blocks, and multi-UUID descriptor layouts. More steps follow; conserve resources.
