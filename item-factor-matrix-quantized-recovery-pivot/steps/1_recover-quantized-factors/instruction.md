Our online retrieval and ranking loads an item factor matrix from a trained checkpoint under /app/ckpt/. To save space the item factors are quantized; the format is described in /app/ckpt/FORMAT.md and the loader is /app/factorstore.py with a function load_item_factors(ckpt_dir) that returns a float32 matrix shaped (num_items, factor_dim). User factors are stored as full-precision floats and are fine.

Most items load and work correctly — nearest-neighbor lookups and scores match offline. But a small slice of high-traffic head items is clearly wrong. Their reconstructed factors look like near-duplicates of unrelated products, their nearest neighbors return unrelated items, and their scores on held-out data don't match. The checkpoint opens with no error via existing load_item_factors, the matrix shape and magnitudes look normal, and spot-checking a few items shows nothing wrong. You only see the collapse when you compare the rebuilt factors for that head slice or run neighbor retrieval.

Fix /app/factorstore.py load_item_factors so it correctly reconstructs the factor matrix for all items, especially that head band. After the fix the function still takes a checkpoint directory path and returns a float32 matrix of shape (num_items, factor_dim). Do not modify any data files under /app/ckpt/ and do not edit /app/ckpt/FORMAT.md — only change the loading logic itself. Note that validation will call your load_item_factors on an unseen checkpoint directory with the same format but different codebooks, codes and items, and compare each item's factor to ground truth including head items, so don't hardcode values from the current checkpoint.
